# 第 26 章　MLOps 与治理

> **对应原书**：Chapter 26 *MLOps and Governance*（第 697–717 页）
> **一句话读懂**：上线不是终点，每个模型都会衰退。这一章讲上线之后怎么「早发现、稳应对、自动兜底」：用数据闸门、滚动指标和漂移检测发现问题，用影子模式和分阶段放量安全换模型，用多层熔断在突发事故时自动止血。配套的 MLOps 工具要按团队规模取用，不要一上来就全套。

---

## 先说结论：这章到底想让你记住什么

如果你只有 3 分钟，记住这 5 点就够了：

1. **先分清 bug 和衰退。**同样输入得出不同输出，是代码问题；输出没变却不再赚钱，是模型问题。弄反了，要么白调试，要么白换模型。
2. **很多「漂移」其实是脏数据。**陈旧报价、公司行为没处理、时区错位、缺 K 线、重复行，会先伪装成统计异常。交易用的数据校验不过，就不交易。
3. **漂移有三种，各用各的尺子。**输入分布变了、特征重要性变了、特征和结果的关系变了。检测到漂移不等于要行动，要结合业绩判断。
4. **换模型走流程：影子 → 小资金 → 逐级放量 → 随时能回滚。**晋级标准事先写死，既要显著也要够大；回滚要演练过。
5. **熔断是最后一道防线：简单、自动、分层。**触及硬上限就停，别想着做回来。

下面逐个展开。

## 26.1 实盘失败的两种来源

第 25 章已经区分过这两类失败，这里换成「医生问诊」的思路再看一遍。

**第一问：同样的输入，现在算出来的结果和回测一样吗？**如果不一样，就是技术性失败：复权价和未复权价混用、数据晚到几秒导致 20 日波动率的窗口不同、符号写反或索引错一位却不报错。这是验证问题，用第 25 章的对账和管道比对去抓，然后修代码。

**第二问：结果一样，但还赚钱吗？**如果不赚，就是统计性失败，系统完全按设计运行，只是输出不再预测收益了。背后可能有四种原因，各自的线索不同：

- **回测本来就虚高**：要么学到的是样本内噪声（多重检验会系统性抬高回测），要么回测里有隐蔽的泄露（用了当时拿不到的数据，或剔除了退市股）。这类问题往往上线没多久就显形。
- **市场换了状态**：波动体制变了、相关性断了、特征和收益的关系变了。通常伴随宏观或结构性事件。
- **被别人挤掉了**：同样的规律被更多人发现，收益被套利掉。研究显示，异象一旦公开发表，盈利能力明显下降。这类衰退往往是缓慢、持续的。

应对也截然不同：技术性失败就修，统计性失败就重训、重做或下线。原书的提醒很直白：把衰退当 bug 会陷入徒劳的调试，把 bug 当衰退会做不必要的模型更换。后面所有监控设计都基于一个前提：衰退一定会来，问题只是何时到、能否及时发现。

## 26.2 业绩监控

### 先守数据入口

监控模型之前，先查喂给模型的数据。实盘里相当一部分「漂移」其实是静默的数据缺陷，它们本质上是技术问题，却最先以统计异常的样子出现在下游指标里。办法是在入口加一层轻量的数据合同，用 Pandera 或 Great Expectations 检查每批数据的类型、空值比例、时间戳是否单调递增、主键是否唯一。

关键选择是：**交易用的数据源校验失败就关门（fail-closed），不交易**；非关键的分析管道可以放行，只发警告。校验结果也接进分级告警：主行情 schema 违规是严重级，次要数据的小毛病只到观察级。

> 🧭 **对你的启发**：这一条对 EA 特别实用：报价时间戳停住不动、点差突然异常放大、周末跳空后第一根 K 线缺失，都应该让 EA 先「不交易」，而不是照常按信号开仓。把这些检查写成开仓前的硬性闸门。

### 看趋势，不看总数

总体指标会掩盖趋势：全期夏普还不错，最近一段可能早已明显变差。所以要在滚动窗口上、用扣成本后的实盘收益计算，并和验证期的同一指标对照。几个指标各有分工：

- **滚动夏普（30 / 60 / 90 天）**：最终结果。持续比预期低 0.5 以上，说明回测虚高或市场换了状态。
- **信息系数**：比收益更早报警。行情好时收益还能撑一阵，IC 可能已在下滑。
- **胜率与盈亏比**：把夏普拆开看。胜率降、盈亏比稳，是方向判断变差；胜率稳、盈亏比降，是方向对但幅度估计差或执行变差。
- **回撤深度和持续时间**：比回测里更深、更久，说明进入了模型没见过的环境。

看多个窗口的好处是能区分噪声和趋势：短窗口跌、长窗口稳，多半是暂时波动；所有窗口一起往下走，才是持续衰退。

### 告警要分级，也要克制

告警可以分观察、警告、严重三级。以预期夏普 1.5 的策略为例，30 天滚动夏普跌破 1.0 先记录待查；连续两周低于 0.5 就要尽快调查、考虑降仓；为负超过 30 天或回撤超过历史最大，就触发保护动作。阈值应从回测里校准：历史上衰退之前，指标处在什么水平？什么值能留出足够的反应时间？

更大的敌人是告警疲劳，天天响的系统只会让团队学会无视它。只保留有明确对应动作的告警，用历史数据估算误报率，每加一个指标就重新审视阈值。原书的说法是：一个经常触发、却从不改变仓位、重训节奏或排查优先级的告警，不过是装成严谨的噪声。

### 面板和对照

一个实用的面板应该一眼回答几件事：现在赚了多少、和回测预期差多远（实盘净值叠在回测净值上，两线之间的缺口是最核心的诊断图）、各窗口滚动指标的走势、当前回撤离历史最大和熔断线还有多远、告警灯是什么颜色。

把回测当作要检验的假设：每个指标记下回测值、实盘值、偏差，以及偏差是否超出估计噪声。偏差必然存在，持续单向的大偏差才说明有东西系统性地变了。一个好用的汇总是**兑现率**：回测夏普 2.0、实盘 1.5，兑现率 0.75。即使绝对表现还过得去，兑现率持续下滑也意味着在退化。

### 执行质量会伪装成模型衰退

短期的盈亏波动常常由执行主导：点差变宽、成交率下降、滑点增大、券商限流，都会压低实际收益，而模型预测本身没变。所以要和模型指标并排监控相对回测假设的滑点、实付点差与报价点差之比、成交率和部分成交、信号到成交的延迟分布，再算一个「实际成本 / 模拟成本」比率。执行成本持续高于假设，问题在微观结构或基础设施，这时去重训模型是错的。

### 配套流程

配套代码用美股案例的真实留出期预测流：拿留出期前最后一年做参照，最近窗口做当前，算特征的 PSI 和 K-S、预测得分分布、滚动 IC、胜率和误差。面板分成「输入变了吗」（PSI、得分直方图）和「输出还好吗」（滚动 IC、胜率）两组，于是能分清指标变化是输入变了、关系变了，还是都变了。处理顺序是：看缺口 → 判断技术还是统计 → 推测机制 → 然后才调仓位或更新模型。每一种触发都应对应一个明确动作。

## 26.3 漂移检测

业绩监控告诉你「有东西变了」，漂移检测帮你找出「变的是什么」。

### 三种漂移，三把尺子

**输入分布变了（数据漂移）。**群体稳定性指数（PSI）把当前数据和训练数据按相同分箱比较占比差异：每箱算（实际占比 − 预期占比）× ln（实际占比 / 预期占比），再求和。经验读法是 0.1 以下基本没变，0.1–0.25 值得调查，0.25 以上说明模型预测可能已不可靠。PSI 往往先于业绩恶化，是提前预警。K-S 检验直接比较两个样本累积分布的最大距离，不用分箱，适合连续特征。

**特征重要性变了。**即使输入分布没变，模型依赖哪些特征也可能变。用 SHAP 跟踪三样东西：平均绝对贡献（多大）、贡献的方差（稳不稳）、相对排名（次序有没有洗牌）。核心特征的贡献塌缩或排名持续变化，说明模型可能在依赖一个市场已经不再奖励的关系。

**关系本身变了（概念漂移）。**最隐蔽：输入看着差不多，却不再以同样方式对应结果。比如市场从趋势转为震荡，同一个动量信号从预示上涨变成预示回落，特征分布一点没变，关系却反了。概念漂移有突变、渐变、增量、周期性复发几种形态。在线检测器适合盯它：ADWIN 维护一个可变长度窗口，不断检验近期观测和早期是否有统计差异，一旦发现就把窗口缩到只剩漂移后的数据，适应性强；DDM 只跟踪错误率及其波动，小幅上升发警告、大幅上升报漂移，更轻量但不够灵活。两者都用在预测误差流（预测收益 − 实际收益）上，生产里常用 `river` 这类库。

### 盯什么、多久盯一次

不必什么都监控，重点放在三类特征上：模型最依赖的（SHAP 贡献大）、本身就容易变的（波动大的）、对市场状态敏感的（波动率、相关性、流动性指标）。节奏上，计算便宜的分布检查（关键特征 PSI，K-S 视情况）可以每天跑，SHAP 这种重计算每周跑一次，误差流上的在线检测器则持续运行。

检测器本身也要被监控：记录它报警的频率和连续警告的次数，在误报淹没操作员之前调整灵敏度。一直响却不改变任何决策的检测器已经没用了。

### 把漂移和业绩放在一起看

单看漂移信号容易过度反应，要和业绩交叉判断。用一个类比：漂移是体检指标异常，业绩是有没有症状。

- **指标异常但没有症状**：分布变了，关系还在，说明模型挺稳，继续观察即可。
- **有症状但指标正常**：要么监控覆盖不全，要么是缓慢的概念漂移，应扩大监控范围、检查没跟踪的特征。
- **指标异常且有症状**：漂移解释了衰退，用近期数据重训，或换成针对当前状态的模型。
- **都正常**：照常运行。

流程是检测 → 与业绩关联 → 提出机制假设 → 针对性验证，既不忽视真问题，也不因噪声换模型。

## 26.4 安全地更新模型

新模型完全可能比衰退的旧模型更差。安全更新的目的，是别用一个故障替换另一个故障。

**何时重训。**定期重训（每周、每月、每季）可预期，但可能没必要，也可能来得太晚；触发式重训（夏普破位、PSI 超限、ADWIN 报漂移）响应真实情况，但依赖可靠的监控。常见做法是两者结合：定期为基线，触发式应对异常，频率与策略预期的衰退速度相匹配。

**影子模式。**新模型（挑战者）和现役模型（在任者）接收同样的实时数据，都出预测，但只有在任者下单。对比三件事：两者方向一致的比例（不一致不一定是坏事，但晋级前要搞清原因）；挑战者在真实执行假设下本该赚多少；它承担的风险画像是否意外变化。配套实验里两者逐标的的信号得分相关约 0.61，挑战者不必天天赢，关键是分歧能被观察、归因和审查。影子期要覆盖足够多样的行情，趋势市里好看的模型可能在震荡市失灵；常见默认 60 天，月度调仓的策略至少覆盖两个调仓周期。

**怎么判断真的更好。**光看曲线不够。可以对每日收益差做配对检验；比较夏普时要考虑均值、波动和两条收益序列的相关性，经典的 Jobson-Korkie 检验假设独立同分布且正态，后来有修正和稳健版本，如果挑战者是从大量实验里挑出来的，还要用折扣夏普处理多重检验和非正态；自助法对成对收益重采样（有序列相关就用块自助），直接得到夏普差的置信区间。

显著不等于值得。0.05 的夏普提升即使显著，也未必抵得上部署风险，所以要事先定一个最小效果门槛（比如提升 0.2–0.3）。统计功效同样关键：影子期太短，温和的改进既证实不了也否定不了，噪声大、自相关、肥尾时尤其如此，要么延长观察，要么先做功效分析。

**分阶段放量。**影子通过后，先给挑战者 5%–10% 的真实资金，这一步会暴露影子模式看不到的问题，比如它的信号扎堆在流动性差的标的上、仓位大到会冲击市场。然后按 10% → 25% → 50% → 100% 逐级加，每级都有最短观察期，完整过渡通常 60–90 天。晋级条件事先写死，例如夏普至少高 0.2、在 10% 水平上显著、任何阶段回撤都不超过历史最大，再按换手率和信号噪声校准。

**回滚。**每次部署都必须可逆：在任者完整存档，随时能恢复；事先定义回滚触发条件（回撤、连续亏损天数、系统错误）；回滚流程要实际演练，只存在纸上的流程在压力下会失灵。系统错误、数据源故障这类低层触发自动回滚，速度第一；业绩下滑这类高层触发可以要求人工确认，避免对噪声过度反应。

> 💡 **类比**：这和软件的灰度发布一模一样：先内部试用（影子），再放给 5% 用户（小资金），没问题再逐步扩大，一键回滚按钮始终在手边。区别只是交易系统的「用户投诉」是真金白银的亏损。

## 26.5 熔断与安全

监控和安全更新对付的是渐进衰退；熔断对付突发故障，那时速度比细致更重要。它是写死的简单规则，在复杂系统失灵时保护资金。

### 分层，且各层独立

防线分四层：每一笔订单、每个策略、整个组合、底层系统（基础设施健康和延迟）。任何一层触发都直接停掉自己负责的范围，不必等上层介入。

### 三类交易熔断

**亏损类最重要**：日内回撤上限（如 −2%）防单日灾难，周回撤上限（如 −5%）防持续失血，从峰值的最大回撤（如 −10% 到 −15%）是终极熔断。固定阈值比较粗，最好结合敞口、流动性、市场压力一起用；但一旦触及真正的硬上限，立刻停，不等人工复核，先止血，别想着做回来。

**持仓类**：单一品种（如组合的 5%）、单一行业（如 20%）、相关性上限。它防的是每笔单独看都合理、加起来却押在同一件事上的过度自信。

**异常类**：极端波动（如 VIX 超过 40）、流动性枯竭（如价差是平时 3 倍）、价格错位（如单日波动超 10%）。市场压力下正常关系会失效，在平常环境训练出来的模型可能输出胡话，这时站到场边往往最稳妥。

> 🧭 **对你的启发**：对外汇和黄金 EA，「点差是平时 3 倍就不开新仓」「非农等重大数据前后暂停」「日内回撤到某个比例就全平并锁到次日」都是这一节的直接落地。关键是日内亏损计数要落盘，EA 或终端重启后不能清零。

### 软件熔断器

上面是风控规则；另有一种软件熔断器模式，管的是基础设施韧性：行情源、执行接口这些依赖变得不可靠时，防止故障层层蔓延。两者都需要。它像家里的空气开关：正常时电流照常通过，同时计数失败；连续失败超过阈值（如 5 次）就跳闸，此后所有请求立即失败，不再白白等待超时；过一段时间（如 30 秒）试着放行一个请求，成功就合闸，失败就继续断开。数据源挂了时，你不希望每个预测请求都卡在等数据上，快速失败能保住系统资源、避免僵尸进程。每次跳闸都要告警，每次恢复都要留日志供复盘。系统层常用的阈值是端到端延迟 100 毫秒，超过就暂停交易直到恢复。

### 跳闸之后

先确认告警，弄清是什么触发的、当前敞口多大，决定哪些仓位平掉或对冲；然后诊断，是行情或执行系统的技术故障，还是模型预测出了错，是否由市场异常引发，事件先后顺序如何；恢复前要确认所有组件健康、数据校验通过、市场恢复正常（如果是因异常触发）、根因已修复或确认无害；重启时不要直接满仓，先缩小仓位或回到纸面，确认行为正确再放大。

### 人工推翻

熔断应自动触发，但也要允许授权人员在误触发时推翻。纪律是：每次推翻都记录谁、何时、为什么；要求明确确认风险；限时有效（如 1 小时，到期需续）；事后全部复盘。推翻太容易，熔断形同虚设；完全不能推翻，又应付不了真正的误报，平衡点取决于风险偏好和运营成熟度。

## 26.6 MLOps 基础设施概览

监控和安全是治理的核心，工具只是辅助。小团队完全可以从最简配置起步，需要时再加。

**特征仓库：解决训练–服务偏差。**研究时你在完整历史上随手算特征；生产时要在流式数据上、在严格延迟约束下实时算出同样的东西。日期处理、标准化窗口、缺失值默认值的细微差别，会悄悄拖累表现，这是机器学习系统「隐性技术债」的典型。Feast 一类的特征仓库让特征只定义一次、同时服务训练和推理，自动做时点正确的连接防止前视，特征定义随模型一起版本化；离线库存多年历史供训练，在线库只存最新值供毫秒级推理，两者自动同步。对交易系统而言，它解决的就是「回测时用 pandas 算 20 日波动率，生产时要随新数据增量算同一个东西」的一致性问题。配套代码还演示了一条错误的时间戳规则会造成多大偏差。

**数据版本与血缘。**特征仓库管一致，回答不了「这个模型到底是用哪份数据训出来的」。生产出问题时要分清是数据坏了还是市场变了，就必须能精确复现训练数据。最低要求是每次训练都写一份运行清单：git 提交哈希、数据快照标识、特征集版本、模型注册版本、配置哈希。DVC 用类似 Git 的方式管理大文件，小团队不用专门的元数据平台也能做到可复现、可回滚。

**实验追踪与模型注册。**MLflow 一类工具记录每次训练的超参数、指标和产物，保存带完整血缘的模型版本，管理从预发到生产的阶段切换。在上一节的流程里，注册表记录谁是在任者、谁在影子期、比较结果如何。监管或风控问「模型为什么这么做」时，你要能说出当时部署的版本、上线时间、训练数据和超参数；美联储 SR 11-7 模型风险指引就把血缘和可复现性当作监管要求。此外还需要持久的审查材料：写明用途和已知局限的模型卡、独立验证备忘录、当前监控报告。这些只存在于聊天记录或临时面板里，就谈不上「有效质询、持续监控、成文治理」。

**交易模型的 CI/CD。**常规部分是特征和信号的单元测试、管道集成测试、模型表现的最低门槛测试、部署后的冒烟测试；机器学习特有的是自动部署闸门：验证指标不过、影子对比退化、回滚未验证，模型就进不了生产。用 GitHub Actions 等工具编排，不靠人记得去跑。

### 按规模配置

与其照搬一张工具清单，不如按「现在最痛的是什么」逐步加：

- **一个人或小团队**，最痛的是可复现：认真写文档的 pandas 特征代码、带版本的模型目录（大文件用 Git LFS）、cron 定时任务、按清单手动部署、一个简单面板，就够了。
- **团队在长大**，最痛的是一致性和协作：加 Feast 保证特征一致，MLflow 和 DVC 管实验与数据版本，Prefect 或 Dagster 编排带重试的工作流，GitHub Actions 自动测试，Prometheus + Grafana 监控，结构化日志里用统一的运行、策略、订单关联 ID。
- **规模化生产**，最痛的是可审计和弹性：支持实时服务的完整特征仓库、带审批流的模型注册、Kubernetes 编排部署、用 OpenTelemetry 打通从信号到执行的全链路追踪。

原书的建议是从比你以为需要的更简单的配置开始。基础设施为交易系统服务，监控和安全做对了，比工具选得多高级重要得多。

## 26.7 本章小结

- 核心是诊断：技术性失败（管道 bug 导致输出错）和统计性失败（输出没错但不再预测收益）需要完全不同的应对，混为一谈既浪费时间又浪费钱。
- 治理分三层：**检测**（数据闸门 → 滚动业绩 → 执行质量 → 漂移诊断：PSI / K-S 看输入，SHAP 看重要性，ADWIN / DDM 看关系）；**应对**（影子、限额 A/B、分阶段放量，换模型不引入新故障）；**自动安全**（多层熔断在亏损、敞口或基础设施越界时停止交易）。
- 特征仓库、数据版本、模型注册、工作流编排这些设施，要按运营成熟度逐步配置，而不是整套照搬。

下一章《系统化优势》会退后一步：当从数据到建模、部署、治理的整条流水线作为一个持续验证的整体运转时，真正的优势从何而来。
