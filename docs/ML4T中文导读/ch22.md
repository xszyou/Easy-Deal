# 第 22 章　用 RAG 做金融研究

> **对应原书**：Chapter 22 *RAG for Financial Research*（第 596–618 页）
> **一句话读懂**：大模型会一本正经地编数字，金融场景容不得这个。RAG 的办法是让模型「只看你给它的材料说话」，并且每句话都能指回原文出处。它不是一句提示词技巧，而是一整套从解析文档到检查引用的工程系统。

---

## 先说结论：这章到底想让你记住什么

如果你只有 3 分钟，记住这 5 点就够了：

1. **幻觉修不掉，只能拦住。**模型是按概率续写的，写得顺不等于写得对。办法只能是架构上的：答案必须来自可核查的材料。
2. **入库决定上限。**表格拆散了、标题丢了、日期没标，后面检索和生成再强也救不回来。
3. **检索要语义和关键词两路并行。**向量懂意思但认不准代码编号，BM25 正相反，合并起来最稳。
4. **算术别交给大模型。**让它找证据、写解释，数字用代码算。
5. **出了错先分类再修。**没找到、找太杂、说错了、算错了、该说不知道却硬答，五种毛病五种治法。

下面逐个展开。

---

## 22.1 从「抽特征」到「生成答案」

第 10 章的 FinBERT 一类模型能给句子打情感分、贴风险标签，输出可以直接当信号用。但它只能在一套固定标签里选：能告诉你这段话偏负面，讲不出为什么，也没法把年报里散在三个章节的信息拼成一个回答。而分析师真正关心的，往往是「欧洲业务为什么增长、管理层又提了哪些相关风险」这种开放问题。

大语言模型把任务从「贴标签」变成了「回答问题」：能总结管理层讨论与分析（MD&A）、起草投资逻辑、从监管文件里挑风险点。代价是**幻觉**：语气笃定、语法完美，事实却是错的甚至编的。原书的态度很明确：这是按概率续写的机制自带的，不是某个版本的缺陷；靠人工逐条核查既不现实也治不了本，改对一个答案，模型下次照样会编。所以要从结构上限制它：只在可信、可核查的材料上作答。这就是 RAG 的起点。

> 💡 **类比**：直接问大模型，像问一个记性很好但爱吹牛的朋友；用 RAG，等于让他开卷考试，还要求每个答案都注明「出自第几页」。

## 22.2 用检索增强生成给模型「拴绳」

模型的知识有两种来源：一种是训练时压进权重里的，说不清出处，更新要重训；另一种是放在外部文档库里的，你自己管，能指到页码，换文档就更新。**检索增强生成（RAG）**的立场是：不信模型「记得」的，只信你当场找给它的。

整条流水线可以拆成「一次离线、两次在线」：

- **离线建库**：年报、电话会纪要、研报、监管指引先解析、切块，每块用嵌入模型转成向量，连同原文和出处信息（文件、页码、章节）存进向量数据库。
- **在线找材料**：用户提问时，用同一个嵌入模型把问题转成向量，取最相近的若干块。
- **在线写答案**：材料和问题一起交给大模型，规定只能据此作答，每个论断带出处。

拼接这些部件的「管道活」一般交给框架：LlamaIndex 专注 RAG 本身，LangChain 更通用、适合搭更大的 Agent，Haystack 也是选项。

要提醒的是，固定长度切块 + 通用嵌入 + 纯向量检索这种「最小可用版」，放到术语密集的金融文档上效果会很差。下面几节就是从底层往上逐层加固。

## 22.3 聪明地把文档「喂」进来

### 切块：一刀下去切坏了什么

每隔几百字切一刀最省事，但财务表格会被切成表头和数字两半，「第 7 项 MD&A」这样的标题会和正文分家，风险因素列表会被拦腰截断。模型拿到这些碎片，就可能把两个财年的数字混着用、把话安到错误的章节上。

块的大小是在精度和语境之间拉锯：块小，检索准，但「营收增长 15%」说的是哪块业务、哪一年就看不出来了；块大，语境完整，但向量被稀释成「平均味道」，还占上下文窗口。原书建议从 400–600 token、重叠 50–100 起步，然后把块大小当超参数，在自己的评测集上比较几档召回率再定。

一个实用折中是**父文档检索**，俗称「以小搜大」：用小块去匹配，命中后把它所在的整节交给模型，代价是入库时多维护一层「小块属于哪一节」的映射。

### 解析：先认出结构

更根本的办法是结构感知解析：识别章节、段落、表格、列表层级，而不是把 PDF 当一长串字符。LlamaParse、Docling、Marker 都属于这一类。工具迭代很快，挑的标准只有一个：结构保没保住。扫描件要过 OCR、多栏排版、跨页脚注、图片格式的表格，都可能让解析器出错，所以上规模前先拿一批有代表性的文件试。

配套代码在 5 家公司的 10-K 上比过：结构感知解析把表格保留度从约 0.45 提到 0.85、版式保真度从 0.40 提到 0.88，解析耗时多了约 70%。

对表格、图表、图片，可以按「信息是否独有」来决定花不花钱：表格必须处理，定量问题的答案大多在里面；图表只有在含有正文里没有的数字时，才值得调一次视觉模型；ColPali 这类直接把整页当图片索引的思路能绕开解析错误，但会丢掉章节、财年等结构信息，目前还不是生产首选。

### 元数据：引用和防泄露都靠它

每块至少带上文件名、页码、章节，金融场景里最要紧的是**时间**：财年、财季、报告期截止日、实际披露日。这和第 1 章的「时点正确」是同一件事：2024 财年的数据可能 2025 年才公布，做历史研究或回测时必须按「当时是否已公开」来筛，按报告期筛就是偷看未来。元数据一方面让检索可以先圈范围（只看某公司某年），另一方面让答案里的出处可以点回原文核对。

> 📌 **关键一句**：入库时丢掉的表格结构、标题和时间标记，后面任何环节都补不回来。

## 22.4 用懂金融的嵌入模型

嵌入模型的理想状态是：「利率敏感性」和「久期风险」即使字面不同，在向量空间里也挨得很近。通用模型多数在百科和论坛语料上训练，对金融语言有几类典型盲区：多义词（「alpha」在投资里和日常用法不同）、股票代码、专业概念（远期市盈率、契约条款），以及最难的因果关联（加息和房贷负担、债券久期亏损之间的联系）。

FinMTEB 是通用基准 MTEB 的金融版，结论是在金融术语、跨文档、时间指代较多的检索任务上，领域适配模型明显领先。但不同任务上排名并不稳定，原书列出的 2026 年中候选模型（商业的有 Voyage、Gemini、Cohere、OpenAI 等，开源的有 Fin-E5、Qwen3-Embedding、BGE-M3 等）只能当初选名单。

**省资源的两招**：套娃嵌入在训练时把重要信息集中在前几维，截短后仍能用（普通模型直接截断不行）；二值量化把每维压成 1 位，内存省 32 倍，精度损失要在自己的数据上测。

**怎么选**：榜单第一只是假设。挑几十到一百个真实会遇到的问题，标好每题该找到的段落，用召回率、MRR 和延迟比较候选，语料或问题类型一变就重测。配套实验里 bge-large 比 MiniLM 的 MRR 高约 14%，可同一个模型在不同题型之间的差距也差不多这么大，这正说明结论必须在自己的场景里得出。

> 🧭 **对你的启发**：这和你给 EA 选参数是一回事：别人的回测报告只是线索，在你自己的品种和 tick 数据上复现出来才算数。

## 22.5 混合检索与向量数据库

### 两路检索各补一块短板

向量检索能把「盈利担忧」和「利润率压缩」联系起来，却认不准精确字符串：搜「TSLA 的 Form 4」，可能捞回一堆泛泛谈内部人交易的段落，偏偏漏掉真正写着 TSLA 的那份。BM25 这类关键词检索正好相反，代码、实体名、法规编号一抓一个准，换个说法就找不到。混合检索就是两路一起跑，再合并排名。

### RRF：奖励「两边都说好」的文档

合并最常用倒数排名融合（RRF）：每份文档在每个列表里得 `1/(k+名次)` 分（k 常取 60），各列表相加，不在某个列表里就记 0。它天然偏爱在两路都靠前的文档，而不是一路第一、另一路垫底的。举个自己的例子：搜「某公司 锂矿 供应」，一段只在页脚提了公司代码的文字可能关键词排第一、语义排很后；一段详细讨论锂原料采购但只出现一次代码的文字两边都在前十，RRF 会把后者排上去，这通常也是分析师真正想看的那段。

RRF 不用训练、很稳。配套实验里混合检索的 MRR 比纯 BM25 高约 27%；反过来，**直接套用网上通用的重排模型，MRR 反而掉了 36%**，现成重排器未必适应金融文本。

### 检索架构怎么取舍

从快到准有三档：双编码器（问题和文档各编一个向量，点积打分，快但丢细节）、后期交互如 ColBERT（每个词都存向量、逐词匹配，索引大、效果居中）、交叉编码器（问题和文档拼在一起让模型打分，最准也最慢）。多数金融 RAG 的务实组合是双编码器初检、交叉编码器重排；反复调优仍总漏东西时，再考虑后期交互。

### 先把问题问对

「他们中国那边怎么样了」这样的原始问题，主语、对应的年报用语、时间范围全都模糊。三个补救：**扩展**同义说法（中国业务 → 大中华区、亚太）；**HyDE**，先让模型写一段假想答案再拿它去检索，对口语化问题有效，但多一次调用，假想答案跑偏了检索也跟着偏；**拆解**比较类问题，比如两家公司的研发对比分成两路检索，因为同时谈两家的段落可能根本不存在。

### 向量库：先过滤，再找相似

产品名单变得快，判断标准更耐用：能否在近似最近邻搜索之前按元数据过滤、能否顺畅接上混合检索、和现有运维体系是否合拍。生产上可选原生支持混合检索的库，原型阶段 ChromaDB 加一个 BM25 索引就够，已经在用 PostgreSQL 或 Elasticsearch 的就用自带方案。

过滤顺序很要紧。先圈定公司、财年、文件类型再搜相似，召回有保障；先全库搜再剔除，目标范围很小时可能一条不剩。更隐蔽的风险是：问「管理层对 2024 年的指引」却不限定文件年份，系统可能找到 2022 年报里顺带展望 2024 的一句话，答案有理有据、引用规范，内容却早过时了。

## 22.6 重排与「带约束」的提示词

### 先求全，再求精

检索阶段宁多勿漏，返回几十块；重排阶段用交叉编码器逐块打分，只留前五块左右给大模型。重排 50 块多花一两百毫秒，分析场景完全可以接受。

### 长上下文不是万能药

窗口已经到了十几万甚至上百万 token，为什么不把整份年报塞进去？三个原因：模型对长文本中段的注意力偏弱；费用按输入算，能用 5K 解决的事塞 200K 不划算；首字返回更慢。原书建议精准检索为主，长上下文留给复杂的多跳问题兜底。

### 提示词当合同写

一份靠谱的 RAG 提示词，至少把这几件事写明白：你是谁（比如做尽调的分析师）、只能用给定材料、材料不够时怎么说、每个事实要带什么格式的出处、答案按「结论 → 证据 → 局限」组织。

即便如此，引用也不等于可信：模型可能引了一段并不支持结论的话、把几块内容揉在一起，甚至编出不存在的页码。一个不必再调用大模型的轻量检查是：按引用位置取回原文，算它和论断的语义相似度，低于阈值的送人工复核。

### 数字题走四步

「营业利润率同比变了多少」这类问题，模型常常找对了表却算错了数。这和幻觉不同，证据没错，推导错了。可靠的做法是：检索证据 → 把数字连同单位、期间、分部抽成结构化格式 → 用代码计算 → 让模型写说明并附计算过程。即使不上 Agent，只要求模型输出抽取值和计算结果的 JSON，再用程序复算一遍，就能拦下大部分数字错误。

再往外一层是程序化护栏：用 JSON 模式或函数调用锁定格式，逐条论断对照材料核验，用 NeMo Guardrails、Guardrails AI 这类框架限定话题和格式。原书把模型的角色概括为说清「证据支持什么」，而不是「知道答案」。

> 🧭 **对你的启发**：做 AI Agent 工具时，如果要模型读回测报告、算胜率或盈亏比，也走「抽取 → 代码算 → 模型解释」这条路。模型读报告在行，让它心算夏普就是自找麻烦。

## 22.7 诊断 RAG 管道的瓶颈

### 先把错误分对类

拿几个问题一试感觉不错，是最危险的信心来源。下面按「你会看到什么 → 问题出在哪 → 先动哪儿」来整理五类失败：

| 你会看到什么 | 问题出在哪 | 先动哪儿 |
|---|---|---|
| 库里明明有，答案却说没找到 | 检索：召回不够 | 嵌入模型、混合权重、切块方式 |
| 答案方向对但掺了无关内容 | 上下文：噪声太多 | 重排阈值、元数据过滤、块粒度 |
| 材料没问题，结论却说错或多编 | 生成：不忠实 | 提示词、更强的模型、答案校验 |
| 引用的表格对，数字错 | 计算 | 交给代码，程序复算 |
| 库里根本没有，模型硬编一个 | 不会说「不知道」 | 评测集里专门放无解题 |

计算错误最难发现：引用的证据是对的，常规忠实度指标照样给高分。

### 用什么量

RAGAs 用强模型当裁判，自动算上下文精度与召回、忠实度、答案相关性和弃答质量；FinDER 等数据集提供金融问答的标准答案。RAGChecker 更细，把答案拆成一条条原子论断逐条查证，得到「无支持论断率」，能抓住整体看着忠实、偏偏一个关键数字没根据的情况。裁判模型的打分本身要用一小批人工标注校准，否则只是换了一种虚假的信心。

### 诊断流程

建一个几十到一百题的评测集，带标准答案和出处，覆盖单跳、多跳、比较几类难度，并放进一到两成无解题，请懂行的人审核；跑出基线；按「召回低看检索、精度低看排序、忠实度低看生成」定位；一次只改最弱的环节；上线后用 TruLens 这类工具持续盯着退化。金融场景另加一项：每次都给引用可追溯性打分。

### 安全测试并进同一套尺子

语料里混进恶意指令（提示词注入、检索投毒），或者用户故意绕开约束，系统又能调用工具时，风险会放大很多。原书主张用同一套指标衡量：对抗输入下继续看无支持论断率、引用失败率和弃答表现。配套实验里，只加了输入清洗和「检索感知」的拒答，不换模型，不安全动作率就从 0.50 降到 0，无支持论断率从 1.00 降到 0.25。

更进一步，CRAG、Self-RAG 让系统先自评检索结果够不够好，不够就改写问题、扩大范围重来。每轮多一次调用，交互场景要限轮数，批处理无所谓。这一步已经很像 Agent 了。

## 22.8 应用场景与策略取舍

**10-K 尽调助手。**两三百页的年报，人工找「今年增长靠什么、哪些风险会拖后腿」要几小时，答案还一半在 MD&A、一半在风险因素。RAG 能跨章节回答并给出页码。上线还得配齐权限控制、提示词和检索内容的审计日志、留存策略，以及对外输出前的人工复核（见第 26 章）。

**ESG：分类器还是 RAG？**看你要的是数字还是理解。每天筛几千只股票的量化 ESG 策略，要能直接喂给优化器的分数，分类器批量快、口径统一，但标签体系固定、只能给出置信度、知识更新要重训；准备见管理层、研究某家公司减排承诺的基本面分析师，要的是带出处的解释，RAG 问什么都行、可以直接核对原文、换文档就更新，但只能一题一题地答。成熟机构两样都用：分类器扫广度，告诉你该看谁；RAG 挖深度，告诉你这家公司到底在做什么。

> 💡 **类比**：分类器像体检的血常规，几十项指标批量出结果，标出哪里异常；RAG 像专科医生面诊，能追问、能看片子，但一次只看一个病人。

**生成模型怎么选。**商业 API 能力最强，但文档要出门，很多机构的数据驻留规定不允许；开源权重模型可以本地部署，复杂任务上略弱。在约束严格、材料充分的 RAG 任务里两者差距在缩小。评估时看四点：是否老实遵守「只用材料」、单次成本、延迟、数据能否出门。常见安排是日常问题走开源，复杂分析走商业 API。

**演示之后的工作量。**真正耗时的是：新披露和财报重述的增量索引；语料快照、嵌入、重排器、提示词、生成模型一起打版本，每次回答留存一份「检索包」（问题、命中的块、证据、模型版本、答案）以便复现；受监管环境下删除要走逻辑标记、法律保全和审计日志；按披露周期设置缓存过期。

**监管。**美国券商监管和欧盟《人工智能法案》都已把生成式 AI 纳入文档、监督、透明度要求。具体规则各地不同，原则一致：从第一天就为审计和溯源设计，并尽早拉上合规和模型风险团队。

**13F 机构持仓。**同样的解析技术也能从监管文件里抽结构化数据。把每季度的 13F 持仓连成「机构–股票」网络，可以看出拥挤度：几家大基金重仓同一批股票，一起减仓时会互相踩踏，这种风险在动量、价值因子里看不出来。这张网络也是下一章图模型的天然输入。

---

## 22.9 引出 Agent 框架

本章的 RAG 是被动的：你问，它查，它答。Agent 更进一步，以大模型为「调度员」，配上工具（RAG 检索、网页搜索、代码执行、数据库、行情 API）和记忆，自己规划步骤。最基础的循环是 ReAct：想一步，做一步，看结果，再想下一步，直到完成或需要向人确认。

在 Agent 里，RAG 只是工具之一。「某公司当前 EV/EBITDA 和五年均值比如何」需要查文档拿背景、查数据库拿历史财务、再算比值，一条 RAG 管道做不完，Agent 负责分派。但原书也提醒，流程清楚、步骤固定的任务，一个设计好的固定工作流往往比 Agent 更可靠；Agent 留给真正开放的探索。

行业现状：内部研究助手、文档分拣、面向分析师的检索系统已有一定规模的生产使用；多 Agent 分工协作在论文里常见，但在受监管机构里，凡是会改变外部状态的动作（下单、对客户沟通、改账户）几乎都还要人工确认。Man Group 公开提到用 Agent 生成量化信号，是少数接入实际信号流程的案例。演示和经过审计的生产系统之间，距离仍然不小。

## 22.10 本章小结

- RAG 是在金融研究里用大模型的基本架构：答案来自当场检索的证据，而不是模型碰巧记得的东西。
- 落地要逐层加固：结构感知入库、懂金融的嵌入、混合检索、重排、带约束的提示词，以及用代码算数。
- 元数据和时点正确是生命线：按披露日而不是报告期筛选，否则就是泄露。
- 稳定重复的技能（分类、抽取）适合微调；在不断更新的文档上做有据可查的分析适合 RAG。
- 评估时把检索、上下文、生成、计算、弃答五类失败分开看，标准是「有据可依的有用程度」，而不是读起来顺不顺。

下一章《知识图谱》处理 RAG 不擅长的问题：答案取决于持股链、供应链、传导路径这类**关系**时，需要把实体和关系显式建模。
