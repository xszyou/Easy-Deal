# 第 25 章　实盘交易系统

> **对应原书**：Chapter 25 *Live Trading Systems*（第 672–696 页）
> **一句话读懂**：大多数量化项目不是死在「策略没有优势」，而是死在「实盘系统和回测系统悄悄算得不一样」。办法是让同一份策略代码同时跑回测和实盘，再逐级验证数据、特征、预测、信号、订单都一致，最后靠开机检查、分级熔断和逐步加仓守住真金白银。

---

## 先说结论：这章到底想让你记住什么

如果你只有 3 分钟，记住这 5 点就够了：

1. **实盘出问题有两种根源。**一种是 bug：同样输入、不同输出，必须上线前消灭；另一种是市场变了或回测过拟合，交给第 26 章的监控。不先排除前者，后者无从诊断。
2. **策略逻辑只写一次。**回测时接历史数据和模拟成交，实盘时接行情和券商，没有「研究版」「生产版」两套代码，分歧就从结构上消失了。
3. **订单要当状态机管。**每个状态能转到哪里写死；用客户端订单 ID 保证幂等，崩溃重启也不会重复下单。
4. **结果对不上就逐层二分。**数据 → 特征 → 预测 → 信号 → 订单，哪一层先不同，问题就在哪一层。
5. **上线分阶段。**自检不过不许交易，熔断分级，先纸面再小资金再加仓；交易所和法域限制要一开始就核实。

下面逐个展开。

## 25.1 统一的「研究到生产」框架

### 两套实现，就是两倍的 bug 藏身处

常见的路径是：研究在 Jupyter 里做完，再由另一个人（或几个月后的你）用另一种语言或框架重写成生产代码。此后研究端改了特征要同步过去，生产端修了边界情况却没同步回来。半年后回测年化 15%、实盘 3%，差距是真的，找原因却要花很久。

原书把这类问题叫**技术分歧**：同样的输入，回测和实盘给出不同的输出。它和市场真变了导致的衰退不同，完全是自己造成的。典型的藏身处有：一边用复权价、一边用未复权价，或者回看窗口差一天；研究假设收盘出信号次日开盘成交，生产里数据到达时间参差、执行是异步的；缺失价格、公司行为、代码变更这些边界情况研究时被忽略；把「某股票目标权重 +5%」换算成股数时，两边的取整和流动性处理不同。

### 解法：一份源文件，两种外壳

回测模式下，框架把历史数据喂给策略，按可配置的假设模拟成交；实盘模式下，框架接上券商，把实时数据喂给**同一个**策略并发出订单。配套的两个库就是这样分工：回测库是事件驱动的验证引擎，实盘库提供完全相同的策略接口，再加券商适配器、实时行情和安全控制。决策逻辑不动，变的只是外围。

要做到这一点，有四个前提：数据和执行都走抽象接口，策略不关心数据来自历史库还是 WebSocket，订单不关心发往模拟器还是券商；信号必须是确定的，不能依赖系统时钟、每次不同的随机种子或环境相关的外部状态；回测和实盘共用同一个事件处理内核，一个从历史里重放事件，一个从行情源接收；持仓、订单、策略状态两边维护方式一致，实盘重启能从保存的状态恢复。

这样一来，第 16–19 章的案例策略就不是原型，而是等着接实时数据的生产代码：第 17 章的调仓逻辑直接变成实盘执行策略，第 18 章的成本参数变成实盘成本预算、用来对照实际执行质量，第 19 章的回撤阈值变成由券商封装层强制执行的熔断。

> 🧭 **对你的启发**：MT5 天然是「一份 EA 同时跑策略测试器和实盘」，这是它的一大优势。而你的风洞做法（把 MQ5 移植成 Python 仿真再对齐）恰恰是本章警告的「两套实现」，所以逐级比对、留下对齐证据格外重要。每次改 EA 都要同步改仿真，并重跑一次对齐测试。

## 25.2 接入盈透证券（IBKR）

盈透覆盖全球多资产，可以通过桌面端 TWS、无界面的 IB Gateway、Client Portal API 或机构级 FIX 接入，对需要广泛品种的系统化交易者，它仍是散户能用到的最灵活的选择之一。开发调试时用 TWS，看得见很方便；服务器上无人值守就用 Gateway，资源占用更低。两者都要定期重新认证，自动登录方案存在，但那份凭据等于账户的全部权限，要慎重。

### 连接：按「迟早会断」来设计

`ib_async` 一类的库把回调式接口包装得更顺手。几条硬规矩：每个进程用唯一的客户端 ID，否则会互相踢下线；实盘和纸面账户端口不同，别连错；定期发轻量请求当心跳，超时就当断线；断线后按指数退避重连、重新订阅行情，并在恢复交易前把未完成订单、已完成订单、成交、持仓、账户数值全部重新拉一遍对账。

### 订单和执行成本

市价单保证成交但要付点差和冲击，限价单保证价格但不保证成交，止损单触发后变市价单，快市里滑点可能很大；再配上 GTC、IOC、AON 等有效期属性。原书引用了一项很说明问题的研究：在美国五家券商同时下了 8.5 万笔市价单，往返执行成本从 0.07% 到 0.46% 不等，订单流付费只解释了其中 3.4% 的差异。也就是说，**券商怎么路由你的单，可能比佣金高低更要紧**。IBKR 的自适应订单就是在「快点成交，少担时间风险」和「慢点成交，少付冲击」之间自动权衡。

### 账户、错误和历史数据

持仓以券商回报为准，开盘时和盘中定期对账；持续盯保证金占用，免得被强平；成交回报（价格、数量、佣金、时间）是事后分析和对账的底稿。错误以数字代码回调，最好集中到一个处理器里：全部落日志，严重的升级告警。几类常见错误的应对思路是：连不上先查 Gateway 是否在运行；中途断线就重连并对账；订单被拒先读原因（保证金、代码、交易时段）再说；历史数据请求太快就排队加延迟。

IBKR 的历史数据有频率限制，品种和周期覆盖不一。需要大量历史数据时找专业数据商，IBKR 主要用于近期数据和交叉核对。

## 25.3 接入 Alpaca

Alpaca 提供美股、ETF、期权零佣金交易和加密货币 API，REST 加流式接口很干净，纸面账户不用入金，是第一次做实盘实验最省事的入口。用法上，下单、查持仓、查账户这类命令走 REST，成交、持仓变化、行情事件这类状态更新走流式订阅。但零佣金不等于零成本，路由质量、点差、场所选择照样决定实际执行成本。

**纸面账户能测什么、不能测什么。**它的账户和下单流程与实盘相同，但成交是模拟的，不和真实流动性博弈。所以它是集成测试工具：订单有没有正确执行、持仓有没有跟准、对账是否正常，这些要在纸面上连续跑好几个交易日确认；滑点、冲击、部分成交这些它测不出来。

**和 IBKR 怎么选。**判断标准很简单：策略要不要跨资产、跨国家。IBKR 覆盖约 170 个市场和大量复杂订单类型，代价是会话制认证、接口更复杂、数据按交易所单独收费；Alpaca 限于美股、ETF、期权和部分加密，API 密钥不过期，标准版走订单流付费、付费版才有智能路由。多资产策略离不开 IBKR；只做美股或加密的系统化策略，Alpaca 一般够用。两点额外提醒：加密 7×24 交易，系统要按「永不下班」设计；Alpaca 的加密品种只是子集，原书案例的 19 个币安永续合约里只有 11 个能在 Alpaca 交易，其余要么换场所，要么只记录信号。

**直连加密交易所。**做永续、期权、杠杆就得直接接币安、Bybit、OKX、Deribit 等的 REST 和 WebSocket，CCXT 统一了各家的认证和限频处理。这是散户最接近「直接市场接入」的方式，但交易所同时是撮合方和托管方，有传统金融里没有的对手方风险。**哪里能用、能不能做衍生品、杠杆多大，因法域而异且常变**，这是法律和运营的前提条件，不是策略做完再去查的细节。

### 错误码与幂等键

Alpaca 用 HTTP 状态码报错：认证失败多半是纸面和实盘的密钥、地址配错了；校验失败通常是购买力不足、代码无效或休市；请求过多就退避排队；服务端错误就退避重试并查状态页。

最关键的是**客户端订单 ID**。下单前用 UUID 或「策略 + 品种 + 信号时间」生成唯一 ID 并保存映射；超时后用同一个 ID 重试，原单其实已成功的话券商会返回那张已有订单，真失败了才新建。网络抖动或崩溃恢复都不会造成重复下单。

> 🧭 **对你的启发**：MT5 里对应的是 magic number 加订单注释，或者自己维护一张「信号 ID → ticket」的映射表并落盘。EA 重启后先拿这张表和账户里的实际持仓、挂单对账，再决定要不要补单，而不是「没看到持仓就再开一单」。

## 25.4 QuantConnect 与托管平台

托管平台把服务器、网络、监控、持续更新的券商集成、历史和实时数据、回测引擎打包好，代价是数据源、券商、订单类型都受平台限制。QuantConnect 的 LEAN 引擎是开源的，所以可以在云上部署、本地开发，或在自建服务器上跑同一个引擎，C# 和 Python 都支持，最大卖点是集成而不是速度。

托管还是自建，可以用几个问题来判断：

- **你的规模多大？**小规模时基础设施成本占大头，平台的订阅或分成划算；规模上去后自建通常更便宜，要算出临界点。
- **你有多少工程人手？**人手少，让平台负责监控、告警、升级；人手足，自建能换来任意数据源、券商和执行逻辑。
- **策略有多特殊？**简单策略、流动性好的品种、平台支持的券商，用平台就行；需要定制数据处理或更低延迟，就该自建。
- **代码放在别人服务器上你介意吗？**这是知识产权问题。

平台也很适合作入门学习环境，或在正式自建前快速做原型。防止被锁定的做法是：策略逻辑和平台样板代码分开写；和数据商保持独立关系；平台允许导出代码的话，实际试一下导出的代码能否在别处跑。

## 25.5 订单生命周期管理

### 一笔订单会在哪里出岔子

从「把 AAPL 权重提到 5%」这个内部目标出发，先经过仓位计算、取整、选订单类型，变成「市价买入 150 股」；发给券商后、拿到确认前，这张单子**是否存在是未知的**，网络恰好在这时断了你就不知道它到没到；券商确认并给出订单号后，它开始工作，可能一次成交，也可能分几次部分成交；成交后更新内部持仓，再和券商对账。每一步都可能出错，稳健的系统要尽早发现，而不是让差异越积越多。

### 状态机：把「可能发生什么」写死

订单的主要状态有：已创建（只在本地）、已提交（等确认）、已确认（工作中）、部分成交，以及三个终点——全部成交、已撤销、被拒绝。配套代码更细，有 10 个状态、19 种合法转移，比如加了「撤单中」这样的中间态。状态机是统一框架和券商接口的接缝：回测时框架瞬间模拟转移，实盘时同一台状态机处理券商的异步回调，所以回测里验证过的订单处理逻辑，到实盘原样复现。

真正考验状态机的是三种边界情况：

- **消息乱序**：成交通知可能比确认先到，状态机要能接住。
- **撤单和成交撞车**：撤单请求刚发出，订单就成交了。订单先进入「撤单中」，成交通知先于撤单确认到达，于是撤单作废，审计日志记下「撤单中 → 全部成交」，事后能完整还原。
- **提交后杳无音讯**：先去券商查这张单，再决定要不要重试。

部分成交时持续更新累计成交量、成交均价和剩余量，每笔都同步持仓，可能还要补单。被拒时先看原因：资金不够就等别的订单释放资金，代码无效就记录调查，休市就等开盘，**不要盲目重试**。撤单分情况看：日终撤当日有效单是正常的，盘中被券商撤单说明有问题，要查。

### 日终对账

三样东西要和券商逐项对：持仓（对不上可能是漏了成交、算错了，或有系统外交易）、订单（券商那边有内部没跟踪的「孤儿单」，随时可能意外成交，最危险）、现金（漏成交、费用算错或有外部出入金）。**一旦不一致就暂停自动交易，人工复核后再调整**，自动修正可能把记账错误变成交易错误。

### 崩溃恢复

最危险的时刻是：订单已经发出，系统在记录之前崩了。重启后还要不要再下？解法是提交前就生成并持久化唯一 ID，随订单一起发出；恢复时拿这个 ID 去券商查，查到了就把内部状态对齐，查不到才说明没发出去，用同一个 ID 重试。

## 25.6 用管道验证保证技术一致性

### 先排除 bug，再谈市场

技术性失败是管道和回测分叉，要在上线前用验证测试消灭；统计性失败是管道没错、市场变了或回测过拟合，要靠上线后的监控。即便是第 16 章的回测过拟合概率分析，也默认技术一致。没验证一致性之前，实盘偏离既可能是 bug 也可能是行情，根本没法诊断。

### 逐层比对，二分定位

把回测管道和实盘管道并排，每一层喂同样的输入、比输出：同一时刻的原始数据算出的特征要一样；同一个特征向量得出的预测要一样；同样的预测加同样的当前持仓，优化器给出的目标仓位要一样；同样的目标仓位生成的订单要一样。端到端结果一旦不同，就逐层查中间产物，像二分查找一样找到最先分叉的那一层。

各层最常见的元凶，按层整理如下：

| 层 | 常见元凶 | 实操提示 |
|---|---|---|
| 特征 | 回测偷看了未来（实盘反而是对的）、复权口径不同、缺失值处理不同、时区混乱 | 在多个历史决策日上自动比对特征向量，持续跑 |
| 预测 | 模型序列化跨库版本不一致、预处理不一致、随机种子、float32 与 float64 精度差在深网里累积 | 依赖版本锁死，升级前先跑一致性测试 |
| 仓位与订单 | 求解器容差或设置不同、协方差估计不同、可交易池不同 | 记录优化器输入，出问题时直接重放 |

自动化回归测试的几种形态：日频策略每天早上检查「昨天的实盘信号」是否等于「用同样信息跑回测」的信号，不一致就停到查明为止；每次提交代码时把特征和预测与一组标准答案比对；定期把整条实盘管道放在历史数据上重放，抓住单元测试漏掉的集成错误；测试跑不了时必须显式报「跳过」，绝不能对着空日志静默通过。

诊断时先确认输入真的相同，数据源问题很容易伪装成计算 bug；再看依赖版本，库升级可能悄悄改变边界行为；在每层边界记录输入输出，是最快看出两边从哪分叉的办法。

### 换了交易场所，也是分歧

在 A 交易所的历史数据上训练、在 B 交易所的实时数据上推理，会产生代码验证发现不了的分布漂移：报价习惯（点差、价格精度、时间戳对齐）、费用结构（资金费率算法）、流动性（按成交量排序的结果）都可能不同。首选是训练和推理用同一个场所；做不到就把差异当作显式的验证项来测量和记录。原书的加密案例用币安数据训练、连 OKX 实时数据，这本身就成了验证任务的一部分。

> 🧭 **对你的启发**：外汇和黄金在这一点上尤其要命：不同经纪商的报价源、点差、服务器时区、周末开收盘时间都不同。用 A 经纪商的 tick 回测、在 B 经纪商的账户上跑，本身就是一种分歧。风洞的对齐阶梯可以显式加一级「数据源一致性」检查。

### 案例：技术一致，结果却不同

**加密资金费率策略。**一个 13 特征（3 个资金费率、10 个价格）的 LightGBM 三分类模型，每分钟从 OKX 拉数据、算特征、预测、决定开平仓；离场有两种：预测方向翻转，或价格逆向超过阈值（如 1%）无条件止损。这也说明模型可以在比训练更高的频率上部署，前提是特征计算一致（效果可能不同）。

验证期有正收益，留出期（含 2025 年下半年加密大跌）却没有。第一反应是有 bug，但逐层验证显示两边完全一致。原因是结构性的：资金费率信号让多头集中在小币、空头集中在 BTC、ETH 这类大币，全市场下跌时小币跌得狠得多，隐含的「小币对大币」敞口站到了策略的对立面。亏损分散在整条多头腿上（前三大亏损币种只占约 8%），所以只做大币也救不了，那样只剩一条没对冲的空头腿，已经不是原来的策略了。

这恰好划清了两章的分工：本章问「实盘算的东西和回测一样吗」，这里答案是一样；第 26 章问「在当前市场状态下还该不该交易」，即使管道完全正确，也可能因此暂停。所以这个 OKX 演示被定位为一致性验证的样本，而不是赚钱的策略。

**外汇日频策略**作为对照：留出期和验证期表现一致，没有符号翻转。日频决策、点差窄、工作日连续交易，通过盈透的外汇纸面账户就能同时拿到行情和执行；它的隐含敞口是套息加短期动量，不那么依赖单一的全市场下跌。

**IB 上 20 只美股大盘股的篮子调仓**暴露了两个典型取舍：预热数据直接从下单的同一个券商会话里取，而不是用研究时的数据加载器，避免拿过时价格排序和算仓位，代价是受限频影响、预热慢；成交后靠轮询持仓对账，简单但可能漏掉间隔内的成交，事件驱动对账才是生产级做法。

## 25.7 运营就绪

### 开机先过闸

运营就绪从启动闸门开始，而不是从第一个信号开始。启动时自动回答五个问题，输出一份简短的人类可读报告，任何一项不通过就不许交易：

1. **机器和网络正常吗？**服务器健康、到券商的网络通、行情是新的、数据库和监控等依赖可用。
2. **登对了吗？**凭据有效、纸面 / 实盘设置符合预期、账户权限够用。最危险的是「部分成功」：登上了，却登错了账户、环境或权限集。
3. **账对得上吗？**内部持仓和现金与券商一致，没有上一交易日遗留的孤儿单，上次对账干净完成。
4. **市场在正常运转吗？**该开市时确实开市，没有交易所限制或熔断，价格不陈旧。
5. **安全设置就位吗？**风险上限、单笔上限、熔断开关都可用。

### 熔断：按「你还信任什么」分级

四级熔断可以理解为对系统信任程度的逐级下降：只是觉得信号有点怪，就**停止产生新信号**，已有订单照常；怀疑下单或路由逻辑出了问题、但持仓还能接受，就**撤掉所有挂单**、持仓不动；对系统状态已经没有把握承担风险，就**全部平仓回到现金**；基础设施故障、状态损坏、完全失去信任，就**关停交易进程和相关自动化**。

两条设计要求：每一级都只需一个事先测试过的操作（一条命令、一个按钮），因为压力下多步骤流程会失败，它要求操作者在系统最不可信的时候保持清醒推理；熔断通道要独立于被控组件，策略引擎卡死时，仍然要有一条从券商侧或基础设施侧撤单平仓的路径。

### 运行中的强制安全

配套实盘库有一层统一的安全券商封装，每一笔订单意图到达券商前都要过检查：持仓市值上限、单笔上限、日内亏损熔断、数据陈旧阈值，违反任何一条直接报错不发。

其中两项如果不持久化，就会在最糟的时刻「失效即放行」：日内亏损熔断必须扛得住当天重启，否则一次崩溃重连就把亏损计数清零、重新放行交易，所以每次状态变化都写文件、重连时读回；数据陈旧检查要记住每个品种最后一根 K 线的时间，超阈值的订单一律拒绝。两者合起来，防住了「交易所故障时拿着陈旧行情交易」和「熔断本该锁住却又开仓」这两种最常见的实盘事故。

第三种常见事故靠**启动对账**：连接时把上次关机保存的持仓和挂单，与券商当前状态逐项比对。差异可能来自盘后单终于成交、有人在图形界面手动平仓、订单在系统外被撤、最后一次保存后又来了部分成交。对账不干净就拒绝开始新的交易周期，除非操作者明确重置。

部署循环里另有两条不变式。**训练截止保护**：标签可用日 = 实盘窗口起点 − 预测期。预测 21 天收益、实盘 2025-01-01 开始，训练就得截止到 2024-11-29 而不是 2024-12-31，否则最后一段标签用到了实盘窗口里的价格；这个截止日写进训练元数据，供第 26 章审计。**篮子分状态存档**：意图、尝试、被接受、失败分开记录，而不是压成一个状态字符串，失败篮子一非空就告警。

命令行工具提供了不依赖券商的运维视图：日内亏损计数、熔断锁、持仓快照、挂单，以及影子模式下的健康状态（正常、等待数据、行情静默、休市空闲、券商断开）。这些状态应该由看门狗进程消费，但不能替代看门狗本身。

### 从纸面到实盘

纸面交易验证的是集成，验证不了冲击、真实佣金和真金白银的心理压力。合理的过渡是：纸面跑到订单路由正确、每日对账通过、策略和券商之间没有说不清的漂移；然后**小比例资金首次上线**，目的不是证明能赚钱，而是确认真实成交、费用、持仓更新都符合预期；干净的话逐步加仓，每加一次都是对运营稳定性的又一次测试。过渡期让实盘和纸面（或影子组合）并行，比较信号、下单时机和成交差异，这往往比任何一边的盈亏都更有诊断价值。

### 监管与法域

原书强调这只是 2026 年初的概览，不构成法律建议。美国散户通过券商跑算法不需特别注册，但 5 个工作日内日内交易 4 次以上的账户须有至少 2.5 万美元权益（日内交易者规则），券商须对所有订单做交易前风控；欧盟 MiFID II 约束的是从事算法交易的投资公司（报备、风控、熔断按钮），通过持牌券商交易的散户不直接受约束，但一旦管理外部资金就进入监管范围；印度对散户算法交易规定最细，要券商审批、交易所分配标识，细则常变。

交易税、杠杆上限、场所准入同样可能决定一切，英国印花税、欧洲金融交易税、加密产品限制都可能让一份漂亮的回测变得不可交易。上线前在目标法域确认四件事：这个产品能否合法交易？券商是否支持自动化接入？有哪些税费？适用什么杠杆和保证金规则？这些属于部署检查清单，而不是策略做完后的附录。

## 25.8 本章小结

- 算法交易最常见的失败是回测与实盘之间的技术分歧。同一份策略代码跑两种模式的统一框架，从结构上消灭了一整类 bug。
- 执行路径各有取舍：盈透适合全球多资产，Alpaca 适合美股和加密的快速起步，直连交易所适合加密衍生品，托管平台适合重视便利胜过控制的人。券商路由对实际成本的影响可能大于佣金，法域限制决定了什么能部署在哪里。
- 订单生命周期是一台显式的状态机，要处理部分成交、竞态和崩溃恢复，靠客户端订单 ID 实现幂等。
- 逐层的管道验证在上线前抓住技术性失败；技术一致之后的亏损，才是第 26 章监控要回答的问题。
- 开机自检、分级熔断、持久化的安全状态、启动对账、从纸面到小资金再逐步加仓，构成了生产运行的纪律。

下一章《MLOps 与治理》讲上线之后的事：模型一定会衰退，如何检测漂移、设置熔断、安全地更换模型。
