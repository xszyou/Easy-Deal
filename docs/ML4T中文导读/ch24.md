# 第 24 章　自主 Agent

> **对应原书**：Chapter 24 *Autonomous Agents*（第 640–671 页）
> **一句话读懂**：金融 Agent 应该当成「工作流」来设计，而不是当成一个会聊天的「人格」。推理模式只是一层，真正决定它可不可信的，是显式状态、强类型的工具合同、受限的自主权，以及能完整重放的运行记录。本章的 Agent 只读、只出概率和研究结论，不下单。

---

## 先说结论：这章到底想让你记住什么

如果你只有 3 分钟，记住这 6 点就够了：

1. **Agent 加在传统模型的上游，不替代它。**它适合处理杂乱、不完整、得先判断相关性的证据；标签稳定、结构化、对延迟敏感的任务，照旧用统计模型或规则。
2. **推理模式按需叠加。**先用 ReAct，有分叉型决策再加思维树，评估体系稳了才加反思；每加一层都要有可测的收益，每次运行都设预算。
3. **聊天记录不是状态。**用有类型的状态对象、在决策节点存检查点、冻结工具输出来重放，否则分不清是提示词改好了还是数据变了。
4. **工具决定上限。**合同写清「返回什么、何时用、何时别用」，返回值带出处和时间，日期截止在工具里强制执行。
5. **多 Agent 的价值要靠事后打分证明。**聚合、辩论、主管、校准，每个组件都要通过消融实验证明有用，否则拿掉。
6. **通用研究 Agent 的形态是「操作员 + 技能库」。**少量通用工具，方法论放进可查阅的技能文件和代码库，提示词短而稳定。

下面逐个展开。

## 24.1 从「预测函数」到「Agent 工作流」

传统管道是个固定函数：特征进、预测出。Agent 在它前面加了一层会自己判断的环节：看看手上有什么证据、还缺什么、调哪个工具去补、更新状态，最后才产出结果。这让自动化能伸到更乱的上游：年报、电话会纪要、事件日历、政策声明、市场隐含概率，这些来源格式不一、到达时间不一，用之前得先判断相关不相关。

本章说的「行动」只指信息类行动：查行情、查文件、取证据、做计算、写结构化产物，**不下单**。只读系统更好防护、也更好评估。原书引用的几个公开原型（Bridgewater 的 AIA Forecaster、BlackRock 作者的 AlphaAgents、约 50 个 Agent 协作做战略配置的 Self-Driving Portfolio）也都止步于分析和建议。

金融场景比通用 Agent 多三条硬要求：输出是带校准诊断的概率，不是一段文字；必须守住「决策当时能知道什么」，任何未来信息都让结果作废；每个论断都能追到具体证据和工具调用，供合规审查。

全章贯穿一个例子：估计预测市场上某个问题（宏观、财报、地缘、科技里程碑）的成立概率。流程是读入问题和截止日 → 只搜截止日前的资料 → 多个 Agent 各自给概率 → 合并并校准 → 全部存档 → 事件揭晓后打分。

**哪些情况不需要 Agent**：数据完全结构化、标签稳定，自适应取证只会添延迟；延迟敏感到毫秒以下，大模型太慢；不需要外部证据、能写成固定变换的，整个推理循环都多余。

**自主权分几级**：从只做总结（L0）、给出决策支持和概率（L1）、在人工批准下执行有限动作（L2），一直到完全自主（L3–L4）。实际金融部署大多停在 L1–L2，因为代价不对称：预测错了代价不小，没有策略约束的执行错了可能是灾难。本章代码都在 L1。

和第 21 章的关系：强化学习回答「该做什么」，这里回答「做之前该先知道什么」，两者可以串起来，比如研究 Agent 的概率喂给 RL 仓位策略。

> 🧭 **对你的启发**：这个分级对你的 AI 工具链很实用。读数据、做分析、写报告可以放到 L1；凡是会动 MT5 账户、改 EA 参数、给客户发消息的动作，至少停在 L2，人工确认再执行。

## 24.2 认知架构：Agent 怎么「想」

几种推理模式都建立在思维链之上：把中间步骤写出来，不用微调也能提升多步任务的准确率。

**ReAct 是默认选项。**每一轮想清楚缺什么、调一个工具、把结果吸收进来，直到证据够了。它最大的好处是每个中间结论都能对应到某次工具调用。它的毛病也很好预料，并且各有对策：不记得已经拿到了证据而反复调用，用迭代上限管住；只看一条结果就下结论，用证据充分性检查；两个工具描述重叠导致选错，靠写清楚 schema；前后观察冲突却没人处理，靠显式的状态校验。配套代码让同一套逻辑可切换跑在模拟器、本地 Ollama 或商业 API 上。

**思维树在关键节点分叉。**比如分析一次议息会议，先分出「偏鹰」「偏鸽」两个情景各自取证，再看哪边站得住。不分叉，Agent 容易一开始就认定一个故事，然后只找支持它的证据。代价是调用次数乘以分支数，还要管分支打分和剪枝，所以只在「过早认定」比多花算力更贵时才用。

**反思在任务结束后写下经验教训**，比微调轻、比单次对话里的学习更持久。但没有明确的记忆规则，它会把临时经验变成长期偏见：每条教训要记下在什么时候、什么条件下得出；要有有效期（加息周期的经验不该带进降息周期）；要有衰减和清理；新证据和旧教训冲突时要能回滚。

**怎么组合**：ReAct 打底收集证据，遇到观察冲突时短暂分叉比较，事件揭晓打完分后记一条反思。每种只叠一层，嵌套太深轨迹就没法排查。再加一道**推理预算**：限制工具调用总数、分支数、调和轮数，用完就交出一个标明不确定性的有界结果，而不是无休止地探索。

## 24.3 Agent 的记忆：状态、持久化与重放

### 三层记忆别混用

按时间尺度分：**工作记忆**是当前这一步看到的东西，受上下文窗口限制；**短期记忆**管一次任务，记下试过什么、还有什么没解决、哪里走过死路；**长期记忆**跨会话保存检索索引、运行产物、打分结果、校准历史。最大的工程风险是混用：长期事实只放在上下文里，换个对话被挤出窗口，答案就变了；临时推理不经校验写进长期记忆，过时的假设越积越多。

### 显式状态和重放

聊天记录把指令、证据、推理、工具输出搅在一起，想知道「这个概率是基于哪些证据」只能去解析自由文本。预测 Agent 的最小状态应包括：运行和问题 ID、as_of 与截止日期、带来源和时间戳的证据、未完成子任务、带状态码的工具调用记录、中间概率与置信度、产物状态（草稿 / 审核 / 定稿）。

检查点设在决策边界上，而不是按固定时间：初步取证完、矛盾调和完、最终综合前、交给下游前。

大模型是随机的，同样提示词重跑一次路径可能完全不同，所以重放是调试的核心手段。目标是把「模型行为的变化」和「证据的变化」拆开：冻结某次运行的工具输出，从检查点恢复，换新提示词或新策略在同样证据上重跑，比较轨迹和指标，只接受让指标变好的改动。不这么做，团队会经常把数据漂移误当成提示词改进。

> 💡 **类比**：这和回测时固定随机种子、固定数据快照再比两个参数版本是一回事。数据每次都在变，你就说不清是参数的功劳还是行情的功劳。

### 记忆也要治理

需要事先定好：原始工具输出保留到打分完成再加一段缓冲，中间推理评估完即可过期；过时教训在变成偏见前退役；可复用证据必须带足元数据，能证明当时已可得；新旧冲突时旧记录是标记、归档还是删除；每个检查点带 schema 版本，重构后历史产物仍能比较。

记忆和评估绑在一起：校准要大量「预测–结果」对，消融要原始运行的中间产物，存得不全，评估就退化成讲几个例子。所以记忆设计既是软件问题，也是模型风险问题。配套代码设了三道闸门：所需证据类型是否齐全、证据是否在允许的时间窗内、代码是否对得上且没有截止后的数据。

## 24.4 工具集成：合同、控制与上下文工程

在金融里，工具设计常常比提示词甚至模型选择更能决定 Agent 的质量。本章涉及的工具分四类：行情（价格、隐含波动率、财报日期）、文档（年报、纪要、研报）、搜索（新闻、监管公告、宏观发布）、确定性计算（收益、回归、评分）。下单调仓属于另一层，不在本章范围。

### 合同写不清，复杂度就流进提示词

一份工具合同要讲清：用途和范围、参数类型和取值、错误语义（暂时失败还是永久失败）、每个返回值必带的出处字段。合同含糊，模型就得猜，比如猜某个价格是否复权，总有猜错的时候。工具描述里最常被省略、又最要紧的一句是「什么时候别用它」。最常见的 Agent bug 几乎都和工具有关：有专用工具却调了宽泛工具、确定性错误还在反复重试、参数缺失触发了静默默认值、新旧证据混用不看时间。对策是调用前校验参数、按错误类型区分重试、必填字段缺失时让流程停下。

### 每一步只给该看的

上下文工程就是有意识地控制模型每一步看到什么。把累积的全部内容塞进每一步，既费 token 又添噪声。每一步只暴露与当前任务相关的状态字段、当前阶段适用的工具、符合时点边界的证据、下游能确定性解析的输出格式。多 Agent 管道也一样，每个专家只拿与自己视角相关的证据。

### 结构化输出和来源策略

下游是代码时，输出就该是结构化对象，工具返回默认带来源 ID、发布时间和检索时间、可定位的段落或记录键、是否在白名单内的标记。这样能快速回答：这条证据决策日是否已可得？来自哪个工具哪个来源？能否从存档复现？主流供应商的 JSON 模式、强制工具调用、按 schema 校验，把校验从事后解析挪进了生成过程。证据不足时应返回结构化的错误或弃答对象，而不是悄悄退回自由文本。

搜索工具要有明确的来源策略：域名白名单、与截止日绑定的日期约束（在工具层强制）、每条结果附来源元数据。失败也分情况：暂时故障就重试，工具挂了就走备用路径，违反策略就拒绝并上报，关键证据缺失就明确弃答，绝不编。

MCP（模型上下文协议）统一了跨供应商的工具接入。务实做法是延迟敏感的核心工具先直连，互操作收益明显的地方再接 MCP。

> 🧭 **对你的启发**：搭 Agent 工具时，「何时别用」和「返回值带时间戳与来源」最容易被省略，偏偏是它们决定 Agent 会不会拿错数据、用到未来数据。日期截止写进工具函数里硬检查，比写在提示词里可靠得多。

## 24.5 工程栈：框架选择与迁移路径

框架之争常被讲成跑分比赛，但对金融 Agent 真正卡脖子的是状态是否可见、能否重放、策略能否强制执行。业内经验也是：价值来自和专有工具、数据控制、评估闭环的集成，而不是框架本身。框架换得很快，原则不变：**能用更少样板代码守住这些性质的框架就用，把它们藏起来的框架跑分再高也别用。**

按需求粗分：要最小开销、完全自控，用原生 SDK 加强类型 schema；要快速搭 ReAct 原型，用轻量 Agent 框架；以检索为中心，用检索优先的框架；生产级研究管道需要持久执行和重放，选带状态图的框架；多角色协作才考虑角色编排框架。

少返工的顺序：原生 SDK + 强类型输出搭出第一天就能测的基线 → 加显式状态和轨迹记录 → 加检查点和重放 → 只有评估证明多样性或辩论确实胜过单 Agent，才上多 Agent。要避开的是：单 Agent 还没跑通就上多 Agent、安全交给框架默认值、上线后才补可观测性、拿换框架代替评估。

原书用同一个任务对比了纯 Python、CrewAI 风格、LangGraph 风格三种写法：原生写法调试最方便但要手动编排；状态图框架带持久化和可视化，状态转移写在图定义里，审查和排障更容易，代价是与框架耦合。配套的 aia-forecaster 仓库则把 notebook 流程封装成了可运行的预测服务。

## 24.6 第一个综合案例：单 Agent 研究员

设计刻意做得很窄：只有一个网页搜索工具，截止日期在工具边界强制；每一步只能输出两种 JSON 动作之一，要么搜索（给查询），要么预测（给概率和理由），动作空间小到不可能选错工具；默认最多 5 步，用完还没预测就记录一个标明高不确定性的默认值，而不是硬凑一个自信的答案。

预测之后再抽取置信度、五档情绪、关键发现与疑点、证据质量（查了几次、几个来源），连同完整轨迹和 token 消耗一起存档。轨迹可序列化成 JSON 做检查点往返和跨运行比较。预测质量差时，它能告诉你是没搜到关键证据、JSON 解析失败，还是理由根本没理会检索结果、只凭模型先验在说话。这些毛病到多 Agent 阶段会更贵，所以先在这里解决。

升级到多 Agent 之前，基线应做到：多次运行成功率稳定、证据扎实度过线、强制默认很少、能从存档复现、token 效率合理。结果不好时，按这个顺序查：**先工具合同和搜索质量，再解析和抽取，最后才是提示词措辞。**

## 24.7 多 Agent 预测系统

### 架构

借鉴 AIA Forecaster（搜索 + 主管调和 + 校准）和 AlphaAgents（专家角色 + 辩论），整条管道是：接收问题、结算规则和市场基准价，记下决策时间与截止日 → 多个 Agent 在同一截止规则下并行研究 → 合成初步概率 → （可选）多空辩论 → 主管梳理分歧、必要时补搜 → 校准、发布、存档、揭晓后打分。

### 分歧本身是信息

同一个提示词，各 Agent 因为自己发出的搜索不同、拿到的结果不同，也会产生差异。原书两个实验：「美国 2026 年底前是否衰退」证据基本一边倒，三个 Agent 给 0.12、0.22、0.22，接近市场价 0.175；「美联储 2026 年是否加息」证据两边都有，三个 Agent 给 0.35、0.58、0.38，指定的多空角色辩论三轮仍差约 0.4。分歧大小反映的是问题本身有多大争议，不是一个可以随手调的参数。真正该警惕的是所有 Agent 结果一模一样，那多半是温度设置坏了或有结构性 bug。所以辩论和专家角色是要在目标问题集上评估的配置：争议题上能挖出分歧，单向题上只是多花钱。

### 聚合：多一个人，多多少信息

合并方式（均值、中位数、截尾均值、按历史可靠性加权）都隐含着对 Agent 间相关性的假设。**极端化**的直觉是：几个真正独立的人都说 70%，合起来的证据应强于 70%；如果他们看的是同一批资料，多一个人几乎没多出信息。Neyman 的极端化系数就随 Agent 数量和平均相关性变化：越独立推得越远，越相关越接近直接取均值。结论很朴素：加 Agent 只有在带来真正不同的证据时才有用。

### 辩论和主管

最简辩论是多头讲最强理由、空头挑战假设和来源，可选第二轮聚焦未解决的矛盾，然后交主管。如果辩论在样本外打分上的提升抵不过成本和延迟，就关掉。主管负责调和，不是证据的替代品：梳理共识与分歧、评估证据质量、决定是否补搜、给出带理由和注意事项的最终产物。它只有在自己置信度高时才能推翻聚合结果，避免最后一次模型调用压倒前面所有证据。

### 校准

大模型的原始概率往往不准，而且倾向向基准率靠拢、不敢下重注。校准让「说 70% 的事大约七成真的发生」，常用 Platt 缩放（逻辑函数变换）。要小心的是：聚合时已经极端化，再叠 Platt 缩放可能双重放大信心，除非两者用的数据不重叠，配套代码在两者同时开启时会报警。正确流程是留一段已揭晓事件只用来拟合，在不重叠的窗口上评估，按固定节奏检查漂移再重拟合。常见坑：样本太少、拟合和评估窗口重叠、没有漂移证据就频繁重校、只盯着校准误差下降却没发现预测变得不敢下判断。

### 评估：分数、消融、基准

评分用几样互补的指标：Brier 分数（概率与 0/1 结果之差的平方均值）、对数分数（重罚自信的错误）、期望校准误差（预测概率与实际频率的偏差），再加锐度（敢不敢给出远离中间的概率）。锐度高而不校准的系统最危险。

消融要至少比较：单 Agent 原始概率、聚合未校准、聚合已校准、去掉主管、减少 Agent 数、市场基准。要回答的是：辩论扣除成本后改善分数了吗？主管推翻减少了大错还是添了噪声？校准是否以牺牲锐度为代价？汇总指标会掩盖系统性错误，还要看错误集中在哪类事件、高概率区间是否过度自信、大失误中有多少来自主管推翻、失败前 Agent 是否已有明显分歧。

和市场共识比较有两个陷阱：问题未揭晓时，市场价和 Agent 预测都只是估计，不能默认市场是真相；在已揭晓问题上打分时，最大风险是**污染**，搜索工具可能取回了截止后的文章，表面跑赢其实是泄露。站得住的做法是时间不重叠、强制截止、报告不同校准方案和随机种子下的区间，单次「赢了」只当演示。每个组件用同一把尺子决定去留：是否改善已揭晓结果的指标、在不同子集上是否稳定、成本延迟能否接受、是否增加策略风险或运维脆弱性。看起来复杂不是保留它的理由。

## 24.8 ML4T 研究 Agent：「操作员」模式

### 任务：把「下一个实验」做出来

第 20 章的九个案例各自留下了数据、特征管道、模型、组合规则、带成本的回测和记录验证结果的注册表，每个案例末尾都写了一句「最值得做的下一个实验」。这个 Agent 的任务就是把那句话端到端地做完。研究迭代没法事先枚举动作，每次的下一步都不同，往往是一小段把现有库串起来的代码，预设动作清单要么无限膨胀，要么把关键动作卡死。

### 操作员 + 技能库

答案和生产级编码 Agent 殊途同归：一个约 880 行的小编排器（原书称为「操作员」），给模型 10 个通用工具（读写文件、运行 bash、查 SQLite 注册表、读 Parquet、列出和读取技能），然后不再插手。

方法论放在另一处：一个 56 篇短文的技能库，分九类，每篇都是「问题 → 错误做法与正确做法对照 → 该调用配套库的哪个函数」。这些内容不进提示词，模型在碰到方法选择（这个夏普要不要折扣？面板数据上怎么算 IC 才不泄露？）时，用 `list_skills`、`read_skill` 按需查阅。防前视偏差、正确计算横截面 IC、不天真计算夏普的纪律，都住在技能文件和库里。关键的反转是：**提示词短而稳定，可查阅的知识随方法论一起增长。**

### 两次真实运行

- **ETF 案例**：任务是把三类最强模型的预测做集成，看能否稳住 LSTM 基线的夏普。Agent 查注册表挑出各模型族的最佳预测，读了 IC 和折扣夏普的技能，做横截面 z 分数平均，按基线原配置重跑。结果 IC 更高（0.065 对 0.052），但验证期夏普更低（0.56 对 0.92），九折里有三折 IC 为负，被组合分配放大了。一个干净的阴性结果，用了 39 轮工具调用，约 1.25 美元。
- **美股公司特征案例**：任务是只保留市值前三个四分位，检验对小盘股的依赖。Agent 找到滞后市值列、算每月切点、过滤信号、按原配置重跑。夏普从 4.27 跌到 2.24，最大回撤从 −15% 加深到 −52%：alpha 还在，但约一半夏普来自小盘股。27 轮，约 0.95 美元。

一阴一阳，这正是正常研究的样子。换案例只需加一条任务配置，因为方法论不在操作员里；每次工具调用和技能读取都在轨迹里，可审计。要防的是模型端的毛病：编造改进、实验没做完就宣布完成、过度解读不确定的结果。沙箱写入、注册表只读、轮数上限、固定模型版本是必需的，但离上生产还差下一节的整套控制。

> 🧭 **对你的启发**：这一节几乎就是你在做的事的样板。把 tick 级回测验证、MT5 对齐、预测流程等方法论写成「问题 + 错误示范 + 正确示范 + 调哪个函数」的技能文件，让 Agent 按需读，而不是把规则全塞进越来越长的提示词；注册表只读，写操作关在沙箱里。

## 24.9 准备上生产

**可靠性靠流程，不靠逐字复现。**Agent 是非确定性的，目标是在变化中保持工作流行为稳定：按失败类型分级的有限重试、失败时明确输出低置信度结果、从最近的正常检查点恢复、工具输出外面套确定性校验。每次运行都留完整轨迹。可观测性分两张表看：工程表盯工具失败、延迟尖峰、状态异常；研究表盯校准漂移、相对基准的差距、消融敏感度，免得把运维事故和模型质量混为一谈。提示词、语料、模型版本都是受监管的产物，几个月后复现不出来的输出，当时再准也是合规风险。

**测试要统计化。**确定性断言不够，要跑 N 次看成功率、违规率、受控输入下的输出方差、滚动窗口里校准的稳定性。截止日期随每次运行传到所有工具，检索按日期过滤，下游再核一遍发布时间，规则在工具边界执行，而不是写在模型的叙述里。

**防污染。**模型可能在训练时「见过」历史结果，于是在截止前的数据上看似能预测，其实是背出来的。对策有：训练期和评估期之间留空档；时间平移测试（评估窗口离训练数据越远，性能是否下降）；避开事后报道泄露的事件窗口；在同一事件集上和基准比。原书的原则是，污染分析和演示效果冲突时，以污染分析为准。

**指标分三块**：研究质量（任务成功率、引用忠实度、工具调用合法率、闸门失败时的弃答质量、单次成本延迟）、预测质量（Brier、对数分数、ECE、锐度）、运维健康（事故率、违规率、重放通过率、漂移告警）。FinBen 基准（42 个数据集、24 类任务）的发现可以用来定预期：抽取和分类还行，预测和数值推理仍弱。按真实事件揭晓打分的平台更严格，也更不怕记忆污染。

**成本和定位。**目前的延迟决定了 Agent 适合研究支持、事件预测、低频决策准备，不适合高速执行。成本按整条工作流算，最有效的是**模型分级**：抽取、格式化、拼参数用小快模型，综合、调和、主管复核用前沿模型，并按阶段盯错误率。另有按截止日做缓存键、调用前压缩上下文、置信度够了提前结束、每次预测设预算上限。以牺牲校准或增加违规换来的省钱不算数。

**发布与运维。**发布前在固定验证集上跑重放和消融，与上一版对比，有退化要明确签字，能灰度就灰度。有研究提出，机构本来就有的投资政策声明（IPS）可以直接充当整个多 Agent 管道的运行边界，类似自动驾驶的「设计运行域」。

**集体效应。**越来越多机构用基于相似基础模型的 Agent，行为可能高度同质，市场模拟显示这会产生异质参与者不会引发的泡沫和流动性危机。所以姿态要保守：行动边界清楚、高影响决策要审批、监控不同 Agent 实例之间的相关性失败。

## 24.10 安全与治理

### 攻击会从哪里进来

沿着一次运行的数据流看：用户输入里可能有恶意提示或畸形查询；检索到的文档里可能埋着注入指令或被投毒的索引，金融文本本身常带祈使语气和投机叙事，更难分辨；工具可能权限过大、参数被滥用或被同名工具顶替；状态可能损坏、复用了过期记忆或丢了出处；输出可能是无依据的论断、过度自信的概率或绕过策略的动作。另有一个贯穿全程的风险：模型自带偏好。研究发现大模型对某些行业和风格有系统性偏好，证据和偏好冲突时还会确认偏误。准确率指标看不出来，要专门测：把同一份证据从对立角度表述，看结论会不会跟着变。多 Agent 能部分缓解，前提是用不同的基础模型或刻意变化的表述。

### 对应的防线

- **注入和投毒**：指令与检索数据严格隔离；证据进入推理前清洗；综合阶段的论断必须链接到具体检索产物；被引来源必须真实存在于证据库；搜索用黑白名单从源头减少可达文档；控制什么能入库并定期扫描索引。
- **最小权限**：只读的工作流，运行时里就不该存在写和执行权限，用只读凭据、按工具限定的密钥、参数范围约束、来源白名单、网络与文件沙箱，并用自动化策略检查来验证，不能只靠文档说明。
- **看守模式**：对会改变外部状态的操作（发通知、写共享库、触发下游），在 Agent 输出和实际执行之间插一个策略代理，逐项校验白名单、拒绝黑名单模式、检查参数范围、限时限资源，每次放行或拒绝都写进不可篡改的日志。配套代码里的看守禁止写操作、过滤含「绕过」「凭据」等词的搜索、留了限流占位；测试中正常搜索放行，查管理员凭据和下单请求被拦下，几类注入载荷（角色覆盖、嵌入交易指令、数据外泄）全部识别，正常金融文本原样通过。顺序上，先在受限权限下证明预测流程可靠，用例真的需要副作用时再加更强的行动控制。
- **人在回路**：有后果的动作要有审批队列、风险或成本超标的阈值闸门、例外双人签字、异常升级；即使只读系统，改配置、换模型供应商、发布策略也要审核。
### 安全要能量化

用对抗场景做测试：检索文本里的注入、试探校验边界的畸形参数、工具重名冒名、过期来源和截止后检索、越权的主管推翻请求。每个场景写明应放行还是拒绝、必须记录哪些日志字段，把安全从口头保证变成可测量的行为。盯住的指标有注入成功率（目标为零）、无支持论断率、违规尝试率、特权调用拦截率、合法调用误拒率、从轨迹定位事故的平均时间。它们和预测评估共用同一批运行产物，不需要另起一套基础设施。

## 24.11 本章小结

- 金融 Agent 是工作流，不是人格。ReAct、思维树、反思只有嵌在显式状态、强类型工具合同、受限自主权和可重放产物里才有意义。
- 三个案例逐级展开：可逐步检查的单 Agent 研究员；取证、聚合、调和分歧、发布概率并事后打分的多 Agent 预测管道；用「操作员 + 技能库」执行研究迭代的通用 Agent。
- 预测支持和市场执行是两类系统。本章刻意只读，因为光是取证、估概率、校准、存档和事后评估，工程和治理要求就已经很高。
- 时点完整性、抗污染测试、可观测性和安全策略，是任何预测质量主张站得住的前提。

下一章《实盘交易系统》讲这些严谨的产物如何在更强的运维控制、监控和故障处理下进入实盘。
